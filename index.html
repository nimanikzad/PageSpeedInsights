اصلاً PageSpeed Insights چیه؟

خلاصه در یک خط: یه ابزار رایگان از گوگل که آدرس صفحه رو می‌گیره و می‌گه این صفحه برای کاربر واقعی چقدر سریع، روون، قابل‌استفاده و استاندارده.

ابزار PageSpeed Insights (که از اینجا به بعد بهش می‌گیم PSI) آدرس صفحه رو می‌گیره و دو جور جواب بهت می‌ده: یکی بر اساس تجربه‌ی کاربرهای واقعی، یکی بر اساس یه تست آزمایشگاهی که همون لحظه اجرا می‌شه. فرق این دوتا رو اگه بفهمی، نصف راه رو رفتی.

🩺 یه تشبیه ساده: داده‌ی واقعی مثل اینه که از ۱۰۰۰ تا مشتری رستوران بپرسی «غذات کِی رسید؟». تست آزمایشگاهی مثل اینه که خودت یه بار با کرنومتر بری بشینی و سفارش بدی. اولی واقعی‌تره، دومی برای پیدا کردن مشکل‌ها عالیه.

👥 بخش اول: داده‌ی واقعی (Field Data)

  • از کاربرهای واقعی مرورگر Chrome جمع می‌شه (به این مجموعه می‌گن CrUX).
  • مربوط به ۲۸ روز گذشته است، پس اگه امروز چیزی رو درست کنی، تغییرش کم‌کم و طی چند هفته دیده می‌شه.
  • ملاکش صدک ۷۵ است؛ یعنی باید دست‌کم ۷۵ درصد بازدیدها تجربه‌ی خوبی داشته باشن تا اون معیار سبز بشه.
  • اگه سایتت بازدید کمی داشته باشه، این بخش خالی می‌مونه. نگران نباش، طبیعیه.
  • این همون داده‌ایه که گوگل برای «تجربه‌ی صفحه» توی رتبه‌بندی بهش نگاه می‌کنه. 🎯

🧪 بخش دوم: تست آزمایشگاهی (Lab Data / Lighthouse)

  • با موتوری به اسم Lighthouse انجام می‌شه که الان نسخه‌ی ۱۳ـش پشت PSI کار می‌کنه.
  • برای موبایل، یه گوشی میان‌رده با اینترنت کُند (شبیه 4G ضعیف) شبیه‌سازی می‌شه. برای همین نمره‌ی موبایل تقریباً همیشه از دسکتاپ کمتره.
  • نمره‌ی معروف ۰ تا ۱۰۰ از همین بخش میاد.
  • هر بار تست بگیری ممکنه چند نمره بالا پایین بشه. این خطا نیست، شرایط شبکه و سرور فرق می‌کنه.
💡 قانون طلایی: برای تصمیم‌گیری به داده‌ی واقعی نگاه کن، برای پیدا کردن و رفع مشکل از تست آزمایشگاهی استفاده کن.

🗂️ این صفحه یا کل سایت؟

توی بخش داده‌ی واقعی دو تا تب داری: This URL (فقط همین صفحه) و Origin (میانگین کل دامنه). اگه صفحه‌ت داده‌ی کافی نداشته باشه، PSI فقط داده‌ی کل دامنه رو نشون می‌ده.

🧩 بخش‌های پایین گزارش Performance

زیر نمره‌ی Performance چند بخش می‌بینی. از Lighthouse 13 به بعد ظاهرش کمی عوض شده:

  • Metrics: پنج عدد اصلی که نمره از اونا ساخته می‌شه (درس ۳ و ۴).
  • Insights: پیشنهادهای تجمیع‌شده که قبلاً اسمشون Opportunities بود؛ مثلاً «Improve image delivery» که چند تا توصیه‌ی قدیمی درباره‌ی عکس رو یکجا آورده (درس ۹).
  • Diagnostics: اطلاعات تکمیلی که مستقیم نمره نمی‌دن ولی سرنخ خوبی‌ان.
  • Passed audits: چیزهایی که قبول شدی. 🎉
📌 خود پیشنهادها (Insights و Diagnostics) مستقیماً نمره رو بالا پایین نمی‌کنن. نمره فقط از ۵ معیار اصلی ساخته می‌شه. پیشنهادها فقط می‌گن چی باعث شده اون معیارها بد بشن.
🔧 یه ترفند: بالای بخش Insights می‌تونی گزینه‌ی نمایش مرتبط با هر معیار رو بزنی (مثلاً فقط مشکل‌های مربوط به LCP). اینجوری می‌فهمی کدوم کار بیشترین اثر رو داره.

Core Web Vitals: سه تا معیار طلایی گوگل

خلاصه: گوگل تجربه‌ی کاربر رو با سه سؤال می‌سنجه: محتوای اصلی زود اومد؟ (LCP) · به کلیک سریع جواب داد؟ (INP) · صفحه نپرید؟ (CLS)
🖼️ LCPبزرگ‌ترین محتوای نمایش‌داده‌شدهبزرگ‌ترین عکس یا متنی که بدون اسکرول دیده می‌شه، کِی کامل نشون داده شد؟
تا ۲٫۵ ثانیه۲٫۵ تا ۴بیش از ۴
👆 INPسرعت پاسخ به تعاملوقتی کاربر کلیک می‌کنه یا تایپ می‌کنه، چقدر طول می‌کشه تا صفحه واکنش نشون بده؟
تا ۲۰۰ میلی‌ثانیه۲۰۰ تا ۵۰۰بیش از ۵۰۰
📐 CLSجابه‌جایی ناگهانی چیدمانچقدر المان‌ها موقع لود شدن بی‌خبر جابه‌جا می‌شن؟ (عدده، واحد نداره)
تا ۰٫۱۰٫۱ تا ۰٫۲۵بیش از ۰٫۲۵

🖼️ LCP دقیقاً چی رو می‌سنجه؟

همون چیزی که یادت بود! مرورگر نگاه می‌کنه بدون اسکرول، بزرگ‌ترین المان صفحه چیه. می‌تونه یه عکس بنر، عکس پس‌زمینه، پوستر ویدیو یا یه بلوک متن بزرگ مثل سرتیتر باشه. بعد زمان نمایش کاملش رو ثبت می‌کنه.

⚠️ LCP کاری نداره اون المان «مهمه» یا «تبلیغه». فقط اندازه برایش مهمه. اگه یه بنر سنگین بالای صفحه گذاشتی، اون می‌شه LCP. محتوای داخل iframe (مثل خیلی از تبلیغ‌های بیرونی) حساب نمی‌شه.

توی گزارش PSI، بخش LCP breakdown بهت نشون می‌ده دقیقاً کدوم المان LCP بوده و زمانش صرف چی شده. درس ۵ کامل بازش می‌کنیم.

👆 INP چیه و چرا جای FID اومد؟

تا مارس ۲۰۲۴ معیار سوم FID بود که فقط اولین کلیک رو می‌سنجید. INP جاش اومد و سخت‌گیرتره: تقریباً همه‌ی تعامل‌ها در طول بازدید رو نگاه می‌کنه و یکی از کندترین‌ها رو گزارش می‌ده.

🛎️ مثل زنگ پذیرش هتل: FID فقط می‌پرسید «بار اول که زنگ زدی، کی جواب داد؟». INP می‌پرسه «توی کل اقامتت، بدترین تأخیری که داشتی چقدر بود؟».
📌 INP فقط توی داده‌ی واقعی وجود داره، چون تست آزمایشگاهی کسی رو نداره که کلیک کنه. توی تست آزمایشگاهی، TBT نماینده‌ی اونه (درس ۴).

📐 CLS یعنی همون «پریدن» اعصاب‌خردکن

داری می‌خونی و یهو یه بنر از بالا میاد و متن می‌ره پایین. یا می‌خوای دکمه‌ی «انصراف» رو بزنی و یهو جاش «پرداخت» میاد! 😱 این جابه‌جایی‌ها جمع زده می‌شن و می‌شن CLS. جابه‌جایی‌هایی که درست بعد از کلیک خود کاربر اتفاق بیفتن (مثل باز کردن یه منو) حساب نمی‌شن.

✅ «قبول شدن» توی Core Web Vitals

بالای گزارش جمله‌ای مثل Core Web Vitals Assessment: Passed یا Failed می‌بینی. برای قبولی باید هر سه معیار توی داده‌ی واقعی (صدک ۷۵) سبز باشن. اگه برای INP داده نباشه، فقط LCP و CLS ملاکن.

⏳ TBT به زبون ساده

مرورگر یه «نخ اصلی» داره که هم جاوااسکریپت رو اجرا می‌کنه، هم به کلیک‌ها جواب می‌ده. هر کاری که بیشتر از ۵۰ میلی‌ثانیه طول بکشه یه «کار طولانی» یا Long Task حساب می‌شه. مقدار اضافه‌ش (مثلاً کار ۱۲۰ میلی‌ثانیه‌ای یعنی ۷۰ میلی‌ثانیه) زمان «قفل بودن» صفحه است. جمع این‌ها می‌شه TBT.

🚪 مثل یه صندوق‌دار تنها: اگه یه مشتری ۱۰ دقیقه وقتش رو بگیره، بقیه‌ی صف هر کاری کنن جواب نمی‌گیرن. TBT می‌گه صندوق‌دار چقدر مشغولِ «مشتری‌های پرحرف» بوده.

🖌️ FCP و Speed Index

FCP اولین علامت زندگیه: «صفحه داره میاد!». Speed Index نشون می‌ده بالای صفحه به‌طور کلی چقدر سریع شکل می‌گیره. هر دو با سرور سریع‌تر، CSS سبک‌تر و حذف فایل‌های مسدودکننده بهتر می‌شن.

🌐 TTFB: معیاری که نمره نداره ولی پای همه چیزه

TTFB زمان رسیدن اولین بایت جواب از سرور به مرورگره. توی داده‌ی واقعی PSI نشونش می‌ده (خوب: ۰٫۸ ثانیه یا کمتر، ضعیف: بیش از ۱٫۸ ثانیه). TTFB بد، همه‌ی معیارهای دیگه رو هم عقب می‌اندازه، چون تا HTML نرسه هیچ اتفاقی نمی‌افته.

🎮 ماشین‌حساب: خودت امتحان کن!

اسلایدرها رو جابه‌جا کن و ببین هر معیار چقدر روی نمره اثر داره. این ماشین‌حساب از همون فرمول و منحنی‌های امتیازدهی Lighthouse استفاده می‌کنه، پس جوابش خیلی نزدیک به عدد واقعیه.

بهینه‌سازی LCP: محتوای اصلی رو زودتر نشون بده

خلاصه: زمان LCP چهار تیکه داره. باید بفهمی کدوم تیکه چاقه و همون رو لاغر کنی.

🧩 چهار تیکه‌ی LCP (LCP breakdown)

  1. TTFB: از وقتی کاربر آدرس رو زد تا وقتی اولین بایت HTML رسید. (سرور، کش، CDN)
  2. تأخیر شروع دانلود (Resource load delay): فاصله‌ی بین رسیدن HTML تا وقتی که مرورگر شروع به دانلود عکس LCP می‌کنه. اگه عکس دیر «کشف» بشه، این زیاد می‌شه.
  3. مدت دانلود (Resource load duration): خود دانلود عکس چقدر طول کشید. (حجم عکس)
  4. تأخیر نمایش (Element render delay): عکس رسیده ولی هنوز نشون داده نشده، چون CSS یا JS جلوش رو گرفته.
💡 توی یه سایت سالم، بیشترِ زمان باید صرف TTFB و دانلود بشه و دو تا «تأخیر» نزدیک صفر باشن.

🔧 جعبه‌ابزار LCP

۱. عکس LCP رو هیچ‌وقت lazy نکن 🚫

اشتباه خیلی رایجیه. وردپرس و خیلی از قالب‌ها همه‌ی عکس‌ها رو lazy می‌کنن، حتی بنر بالای صفحه رو. نتیجه؟ مرورگر صبر می‌کنه تا مطمئن بشه عکس توی دیدرسه، بعد دانلودش می‌کنه.

<!-- ❌ بد: عکس بالای صفحه با lazy -->
<img src="hero.jpg" loading="lazy">

<!-- ✅ خوب: اولویت بالا + ابعاد مشخص -->
<img src="hero.avif" width="1200" height="600"
     fetchpriority="high" alt="…">

عکس‌های پایین صفحه رو حتماً lazy کن. فقط بالای صفحه نه.

۲. بذار مرورگر عکس رو زود «کشف» کنه 🔭

اگه عکس LCP با CSS (مثل background-image) یا با جاوااسکریپت اضافه بشه، مرورگر توی HTML نمی‌بینتش و دیر می‌ره سراغش. Insight مربوطه اسمش LCP request discovery است. راه‌حل: عکس رو با تگ <img> توی خود HTML بذار، یا preload کن:

<link rel="preload" as="image" href="hero.avif" fetchpriority="high">
۳. عکس رو سبک و به‌اندازه کن 🗜️
  • فرمت مدرن: AVIF یا WebP معمولاً خیلی سبک‌تر از JPG و PNG هستن.
  • عکس ۴۰۰۰ پیکسلی رو توی کادر ۴۰۰ پیکسلی نذار. با srcset برای هر صفحه‌نمایش اندازه‌ی مناسب بفرست.
  • برای انیمیشن به‌جای GIF از ویدیوی MP4 یا WebM استفاده کن.
<img src="hero-800.avif"
     srcset="hero-480.avif 480w, hero-800.avif 800w, hero-1600.avif 1600w"
     sizes="(max-width: 700px) 100vw, 800px"
     width="800" height="400" alt="…">

توی PSI همه‌ی این‌ها زیر یه Insight به اسم Improve image delivery جمع شدن.

۴. سرور رو سریع کن (TTFB) 🖥️
  • کش صفحه: HTML رو از قبل آماده نگه دار تا برای هر بازدید از نو ساخته نشه (توی وردپرس با افزونه‌های کش).
  • CDN: فایل‌ها رو از نزدیک‌ترین سرور به کاربر بفرست. اگه مخاطبت ایرانیه، هاست و CDN نزدیک به ایران فرق بزرگی ایجاد می‌کنه.
  • ریدایرکت‌های زنجیره‌ای رو حذف کن (مثلاً http → https → www). هر ریدایرکت یه رفت‌وبرگشت اضافه است.
  • فشرده‌سازی Gzip یا Brotli رو روی سرور روشن کن.

این سه مورد آخر توی PSI زیر Insight Document request latency نشون داده می‌شن.

۵. جلوی «تأخیر نمایش» رو بگیر 🧱

اگه عکس رسیده ولی نشون داده نمی‌شه، معمولاً یه CSS یا JS سنگین جلوش رو گرفته (درس ۸). یا اسلایدری داری که با جاوااسکریپت عکس اول رو نشون می‌ده. اسلایدرهای سنگین بالای صفحه از دشمن‌های اصلی LCP هستن. 🎠

درس ۶ · ۱۸ دقیقه

بهینه‌سازی INP و TBT: صفحه‌ای که فوری جواب می‌ده

خلاصه: دشمن اصلی، جاوااسکریپتِ زیاد و کارهای طولانیه. کمترش کن، تیکه‌تیکه‌ش کن، دیرتر اجراش کن.

⏱️ سه مرحله‌ی یه تعامل

وقتی کاربر کلیک می‌کنه، زمان INP سه بخش داره که توی Insight INP breakdown می‌بینیش:

  1. تأخیر ورودی: نخ اصلی سرش شلوغه و کلیک باید توی صف وایسه.
  2. زمان پردازش: کدی که به کلیک جواب می‌ده چقدر طول کشید.
  3. تأخیر نمایش: مرورگر چقدر طول کشید تا نتیجه رو روی صفحه بکشه.

🔧 جعبه‌ابزار INP/TBT

۱. جاوااسکریپت کمتر بفرست 📦
  • کدی که استفاده نمی‌شه رو حذف کن (Diagnostic: Reduce unused JavaScript).
  • تقسیم کد (Code splitting): فقط کدی رو بفرست که این صفحه لازم داره.
  • کتابخونه‌ی سنگین برای کار ساده نیار. گاهی ۲۰ خط کد خالص جای یه کتابخونه‌ی ۹۰ کیلوبایتی رو می‌گیره.
  • Insightهای Legacy JavaScript و Duplicated JavaScript می‌گن کجا کد قدیمی یا تکراری داری.
۲. اسکریپت‌ها رو دیرتر اجرا کن 🐢➡️🐇
<!-- defer: بعد از ساخته شدن صفحه، به‌ترتیب اجرا می‌شه -->
<script src="app.js" defer></script>

<!-- async: هر وقت رسید اجرا می‌شه؛ برای آنالیتیکس مناسبه -->
<script src="analytics.js" async></script>

اسکریپت‌هایی مثل چت آنلاین یا ویجت‌ها رو می‌شه بعد از اولین تعامل کاربر یا چند ثانیه بعد از لود بارگذاری کرد.

۳. کارهای طولانی رو تیکه‌تیکه کن ✂️

به‌جای یه حلقه‌ی ۵۰۰ میلی‌ثانیه‌ای، کار رو تیکه کن و بین تیکه‌ها به مرورگر فرصت نفس کشیدن بده:

// بین هر تیکه، نخ اصلی رو آزاد کن تا کلیک‌ها جواب بگیرن
async function processAll(items) {
  for (const item of items) {
    doWork(item);
    await (globalThis.scheduler?.yield?.() ?? new Promise(r => setTimeout(r, 0)));
  }
}

کارهای خیلی سنگین (مثل پردازش داده) رو هم می‌شه کامل برد توی Web Worker تا اصلاً به نخ اصلی کاری نداشته باشن.

۴. اسکریپت‌های شخص ثالث رو مهار کن 🧳

آنالیتیکس، پیکسل‌های تبلیغاتی، چت آنلاین، ویجت شبکه‌های اجتماعی، نقشه و ویدیوی امبد شده... هرکدوم سهمی از نخ اصلی رو می‌خورن. Insight 3rd parties نشون می‌ده هر سرویس بیرونی چقدر وقت گرفته.

  • اونایی که لازم نیستن رو حذف کن. 🧹
  • برای ویدیوی یوتیوب و نقشه، اول یه عکس ساده نشون بده و با کلیک کاربر اصلش رو لود کن (روش Facade).
۵. DOM رو کوچیک نگه دار و از Forced reflow فرار کن 🌳

صفحه‌ای که هزاران المان تودرتو داره، هر تغییر کوچیکش گرون تموم می‌شه (Insight: Optimize DOM size). یه خطای رایج دیگه اینه که توی جاوااسکریپت پشت سر هم یه اندازه رو بخونی (مثل offsetHeight) و استایل رو عوض کنی. این کار مرورگر رو مجبور به محاسبه‌ی دوباره‌ی چیدمان می‌کنه (Insight: Forced reflow). اول همه‌ی خوندن‌ها، بعد همه‌ی نوشتن‌ها.

برای بخش‌های پایین صفحه هم content-visibility: auto می‌تونه رندر رو تا وقتی که بهشون برسی عقب بندازه.

⚡ برای دیدن INP واقعی سایت خودت، از افزونه‌ی Web Vitals یا تب Performance توی Chrome DevTools استفاده کن. اونجا INP زنده‌ی کلیک‌های خودت رو نشون می‌ده.

درس ۷ · ۱۲ دقیقه

بهینه‌سازی CLS: صفحه‌ای که سر جاش وایمیسه

خلاصه: برای هر چیزی که دیر لود می‌شه، از قبل جا نگه دار. همین!

توی PSI، Insight Layout shift culprits بهت نشون می‌ده دقیقاً کدوم المان‌ها پریدن و چرا. معمولاً یکی از این ۵ مقصرن: 🕵️

۱. عکس و ویدیوی بدون ابعاد 🖼️

وقتی width و height نداری، مرورگر نمی‌دونه چقدر جا بذاره. عکس که رسید، همه چیز رو هل می‌ده پایین.

<img src="photo.webp" width="640" height="360" alt="…">

/* یا با CSS */
.video-box { aspect-ratio: 16 / 9; width: 100%; }
۲. تبلیغ، بنر و ویجتی که بی‌خبر میاد 📢

برای جایگاه تبلیغ یا بنر یه min-height ثابت بذار، حتی اگه گاهی خالی بمونه. بنرهای «دانلود اپ» و «کوکی» رو هم به‌جای هل دادن محتوا، روی صفحه شناور کن (position: fixed).

۳. فونت‌هایی که دیر میان 🔤

وقتی فونت اصلی (مثلاً وزیرمتن) دیر برسه و جای فونت موقت بشینه، اندازه‌ی متن عوض می‌شه و خط‌ها جابه‌جا می‌شن.

@font-face {
  font-family: "Vazirmatn";
  src: url("/fonts/Vazirmatn.woff2") format("woff2");
  font-display: swap;   /* متن فوراً با فونت موقت نشون داده بشه */
}
<link rel="preload" href="/fonts/Vazirmatn.woff2" as="font" type="font/woff2" crossorigin>

Insight Font display چک می‌کنه که فونت‌ها متن رو نامرئی نگه ندارن. برای کم کردن پرش، می‌تونی با size-adjust فونت موقت رو هم‌اندازه‌ی فونت اصلی کنی. استفاده از فرمت woff2 و فقط وزن‌هایی که واقعاً لازم داری هم حجم رو خیلی کم می‌کنه.

۴. محتوایی که با JS بالای صفحه اضافه می‌شه ⬆️

هیچ‌وقت چیزی رو بالای محتوای موجود اضافه نکن، مگر اینکه خود کاربر کاری کرده باشه. اگه لازمه، از قبل جاش رو خالی نگه دار یا از اسکلت (Skeleton) هم‌اندازه استفاده کن.

۵. انیمیشن با ویژگی‌های اشتباه 🎞️

انیمیشن با top، margin یا height چیدمان رو جابه‌جا می‌کنه. به‌جاش از transform و opacity استفاده کن که هم نرم‌ترن، هم CLS نمی‌سازن.

🧠 نکته‌ی جالب: اگه سایتت از «کش برگشت/جلو» مرورگر (bfcache) پشتیبانی کنه، وقتی کاربر دکمه‌ی Back رو می‌زنه، صفحه آنی برمی‌گرده و LCP و CLS عالی ثبت می‌شه. چیزهایی مثل unload یا هدر Cache-Control: no-store جلوی این کش رو می‌گیرن.

درس ۸ · ۱۴ دقیقه

منابع مسدودکننده، CSS، کش و شبکه

خلاصه: مرورگر تا CSS و JSهای داخل head رو نگیره، چیزی نشون نمی‌ده. مسیر رو کوتاه کن، فایل‌ها رو سبک کن و کش رو طولانی کن.

🚧 Render blocking requests

فایل‌های CSS و اسکریپت‌های بدون defer توی <head> جلوی نمایش رو می‌گیرن. راه‌حل‌ها:

  • CSS ضروری بالای صفحه (Critical CSS) رو مستقیم داخل <style> بذار و بقیه رو بعداً لود کن.
  • CSSهایی که استفاده نمی‌شن رو حذف کن (Diagnostic: Reduce unused CSS). قالب‌ها و صفحه‌سازهای آماده معمولاً پر از این‌ان.
  • فایل‌ها رو فشرده (Minify) کن.
  • اسکریپت‌ها رو defer یا async کن (درس ۶).

🕸️ Network dependency tree

اگه HTML یه CSS بخواد، اون CSS یه فونت بخواد و اون فونت از یه دامنه‌ی دیگه بیاد، یه زنجیره‌ی طولانی ساختی که هر حلقه‌ش یه رفت‌وبرگشت شبکه است. این Insight همین زنجیره رو نشون می‌ده. زنجیره رو کوتاه کن، و برای دامنه‌های بیرونی مهم از preconnect استفاده کن:

<link rel="preconnect" href="https://cdn.example.com" crossorigin>
⚠️ با preconnect و preload زیاده‌روی نکن. اگه همه چیز «فوری» باشه، دیگه هیچ چیز فوری نیست. ۲ یا ۳ مورد واقعاً مهم کافیه.

🗄️ Use efficient cache lifetimes

فایل‌های ثابت (عکس، فونت، CSS، JS) رو با کش طولانی بفرست تا بازدید دوم تقریباً آنی باشه:

Cache-Control: public, max-age=31536000, immutable

برای اینکه بعد از تغییر فایل، کاربر نسخه‌ی قدیمی رو نبینه، اسم فایل رو نسخه‌دار کن (مثلاً style.v3.css).

🚀 Modern HTTP

مطمئن شو سرورت از HTTP/2 یا HTTP/3 پشتیبانی می‌کنه. اکثر هاست‌ها و CDNهای امروزی این رو دارن؛ اگه نداری، وقت عوض کردنه.

📱 Optimize viewport for mobile

این خط باید توی همه‌ی صفحه‌ها باشه، وگرنه موبایل صفحه رو مثل دسکتاپ کوچیک‌شده نشون می‌ده و تعامل‌ها هم کندتر می‌شن:

<meta name="viewport" content="width=device-width, initial-scale=1">

🏋️ Avoid enormous network payloads

مجموع حجم صفحه رو زیر نظر داشته باش. صفحه‌ای که چند مگابایته، روی اینترنت موبایل همیشه کند می‌مونه، هر کاری هم بکنی.

دسترسی‌پذیری: سایتی برای همه

خلاصه: سایتت باید برای کسی که کم‌بیناست، از صفحه‌خوان استفاده می‌کنه یا فقط با کیبورد کار می‌کنه هم قابل‌استفاده باشه. این‌ها معمولاً ساده‌ترین نمره‌هان!
🎨 کنتراست رنگ کافی

متن خاکستری کم‌رنگ روی زمینه‌ی سفید قشنگه ولی خونده نمی‌شه. نسبت کنتراست متن معمولی باید دست‌کم ۴٫۵ به ۱ باشه و متن‌های درشت دست‌کم ۳ به ۱. توی DevTools روی رنگ کلیک کنی، نسبت کنتراست رو نشون می‌ده.

🖼️ متن جایگزین برای عکس‌ها

هر عکس معنادار یه alt توصیفی لازم داره. عکس‌های تزئینی alt="" (خالی) بگیرن تا صفحه‌خوان ازشون رد بشه.

🔘 دکمه‌ها و لینک‌های اسم‌دار

دکمه‌ای که فقط یه آیکون داره (مثل 🔍 یا ☰) باید با aria-label اسم داشته باشه. وگرنه صفحه‌خوان فقط می‌گه «دکمه» و کاربر نمی‌فهمه چیه.

<button aria-label="جست‌وجو">🔍</button>
📝 فرم‌ها با label

هر فیلد فرم یه <label> وصل‌شده لازم داره. placeholder جای label رو نمی‌گیره، چون با شروع تایپ ناپدید می‌شه.

🌐 زبان و جهت صفحه

برای سایت فارسی: <html lang="fa" dir="rtl">. این‌جوری صفحه‌خوان با تلفظ فارسی می‌خونه.

🔢 ترتیب درست سرتیترها

یک h1 برای هر صفحه، و از h2 یهو نپر به h4. سرتیترها نقشه‌ی صفحه برای صفحه‌خوان‌ها و موتورهای جست‌وجو هستن.

👆 اندازه‌ی کافی برای لمس

دکمه‌ها و لینک‌ها روی موبایل باید به‌اندازه‌ی کافی بزرگ و از هم فاصله داشته باشن تا انگشت اشتباهی رو نزنه.

🧩 استفاده‌ی درست از ARIA

قانون اول ARIA: تا جایی که می‌شه ازش استفاده نکن! اول از تگ‌های درست HTML (مثل button، nav، main) استفاده کن. ARIA اشتباه از نبودنش بدتره.

⚠️ نمره‌ی ۱۰۰ دسترسی‌پذیری یعنی خطاهای «قابل‌تشخیص خودکار» رو نداری، نه اینکه سایتت کاملاً دسترسی‌پذیره. یه بار هم خودت فقط با کیبورد (Tab و Enter) سایت رو بگرد. 🎹

Best Practices و SEO: نمره‌های آسون و مهم

خلاصه: این دو بخش بیشتر «چک‌لیستی»ان؛ یه بار درستشون کنی، معمولاً سبز می‌مونن.

✅ Best Practices

  • 🔒 HTTPS برای کل سایت، بدون محتوای مخلوط (عکس یا اسکریپتی که با http لود بشه).
  • 🧯 خطای کنسول نداشته باش. DevTools رو باز کن، تب Console، هرچی قرمزه رو درست کن.
  • 🖼️ عکس‌ها با نسبت ابعاد درست و رزولوشن کافی نمایش داده بشن (کش‌آمده یا تار نباشن).
  • ⛔ از APIهای منسوخ و قدیمی مرورگر استفاده نکن.
  • 🔔 بدون کلیک کاربر، اجازه‌ی نوتیفیکیشن یا موقعیت مکانی نخواه.
  • 🧷 هدرهای امنیتی مثل CSP، HSTS و COOP رو تنظیم کن. این‌ها بیشتر به‌صورت توصیه نشون داده می‌شن.
  • 🍪 وابستگی به کوکی‌های شخص ثالث رو کم کن؛ مرورگرها دارن محدودشون می‌کنن.

🔎 SEO (سئوی پایه)

  • 🏷️ هر صفحه یه <title> یکتا و یه meta description جذاب داشته باشه.
  • 🚦 کد وضعیت HTTP صفحه ۲۰۰ باشه، نه ۴۰۴ یا ۵۰۰.
  • 🚫 صفحه با noindex یا robots.txt اشتباهی از ایندکس بسته نشده باشه.
  • 🔗 لینک‌ها قابل‌خزیدن باشن (<a href="…"> واقعی) و متن لینک توصیفی باشه، نه «اینجا کلیک کنید».
  • 🖼️ عکس‌ها alt داشته باشن.
  • 🌍 اگه سایت چندزبانه است، hreflang و canonical درست تنظیم بشن.
  • 🧩 داده‌ی ساختاریافته (Schema) رو با ابزار Rich Results Test گوگل چک کن.
⚠️ نمره‌ی ۱۰۰ سئو توی PSI یعنی «پایه‌ها درسته»، نه اینکه رتبه‌ی یک می‌گیری! محتوای خوب، لینک‌سازی و نیت جست‌وجو هنوز حرف اول رو می‌زنن. 😉

روش کار حرفه‌ای: از تست تا سبز شدن

خلاصه: اندازه بگیر ← اولویت بده ← یه تغییر بده ← دوباره اندازه بگیر. هیچ‌وقت ده تا کار رو با هم نکن.
  1. صفحه‌های مهم رو انتخاب کن: صفحه‌ی اصلی، پربازدیدترین مقاله‌ها، صفحه‌ی محصول و صفحه‌ی پرداخت. هر قالب صفحه رو جدا تست کن.
  2. اول موبایل: بیشتر کاربرها با موبایل میان و گوگل هم موبایل رو ملاک می‌ذاره.
  3. ۳ تا ۵ بار تست بگیر و عدد میانه رو یادداشت کن، نه بهترین رو.
  4. بدترین معیار رو پیدا کن و با فیلتر Insights ببین چی روش اثر داره.
  5. یه تغییر بده، دوباره تست کن. اینجوری می‌فهمی کدوم کار واقعاً اثر داشته.
  6. صبر کن: داده‌ی واقعی ۲۸ روزه است. توی Search Console هم بعد از رفع مشکل، دکمه‌ی Validate Fix رو بزن.

🧰 جعبه‌ابزار رایگان

  • PageSpeed Insights: نقطه‌ی شروع؛ داده‌ی واقعی و آزمایشگاهی با هم.
  • گزارش Core Web Vitals توی Google Search Console: همه‌ی صفحه‌های سایت رو گروه‌بندی می‌کنه و می‌گه کدوم گروه مشکل داره.
  • تب Lighthouse و Performance در Chrome DevTools: برای تست صفحه‌های محلی، صفحه‌های پشت لاگین و دیدن جزئیات هر میلی‌ثانیه.
  • تب Network: برای دیدن ترتیب و حجم همه‌ی درخواست‌ها.
  • WebPageTest: برای تست از کشورها و سرعت‌های اینترنت مختلف و دیدن فیلم لود صفحه.
  • Lighthouse CI: برای برنامه‌نویس‌ها؛ هر بار که کد تغییر کرد خودکار تست کنه تا سرعت یواشکی بدتر نشه.
# اجرای Lighthouse از خط فرمان (نیاز به Node.js)
npm install -g lighthouse
lighthouse https://example.com --view --preset=desktop

🌐 چند نکته برای سایت‌های ایرانی

  • تست PSI از سرورهای گوگل خارج از ایران انجام می‌شه. اگه هاستت داخل ایرانه، TTFB توی تست ممکنه بدتر از تجربه‌ی واقعی کاربرهای ایرانی باشه، و برعکس.
  • فونت فارسی رو روی هاست خودت بذار (self-host) و فقط وزن‌هایی که لازمه رو لود کن. هم سریع‌تره، هم به سرویس‌های بیرونی وابسته نیستی.
  • اسکریپت‌های سرویس‌های بیرونی (چت، آمار، اینماد، تبلیغات) رو یکی‌یکی بررسی کن؛ معمولاً بزرگ‌ترین منبع TBT هستن.

نکته‌های وردپرس و باورهای غلط رایج

🧩 اگه سایتت وردپرسیه

  • یه افزونه‌ی کش خوب نصب کن (فقط یکی! دو تا افزونه‌ی کش با هم دعوا می‌کنن).
  • عکس‌ها رو موقع آپلود به WebP یا AVIF تبدیل کن و lazy load رو برای عکس اول صفحه خاموش کن.
  • افزونه‌های اضافه رو پاک کن. هر افزونه ممکنه CSS و JS خودش رو توی همه‌ی صفحه‌ها لود کنه.
  • صفحه‌سازهای سنگین و اسلایدرهای بالای صفحه معمولاً مقصر اصلی LCP و TBT هستن. یه قالب سبک خیلی وقت‌ها از ده تا افزونه‌ی بهینه‌سازی بیشتر اثر داره.
  • نسخه‌ی PHP رو به‌روز نگه دار؛ نسخه‌های جدیدتر سریع‌ترن.

🙅 باورهای غلط

❌ «باید حتماً ۱۰۰ بگیرم»

نه! خود مستندات Lighthouse می‌گه نمره‌ی ۱۰۰ خیلی سخته و انتظارش نمی‌ره. هدف واقعی، قبول شدن Core Web Vitals توی داده‌ی واقعیه. سایتی با نمره‌ی ۸۵ و Core Web Vitals سبز، از سایتی با نمره‌ی ۹۹ و کاربرهای ناراضی بهتره.

❌ «نمره‌ی PSI مستقیماً رتبه‌ی گوگل رو تعیین می‌کنه»

گوگل از داده‌ی واقعی Core Web Vitals به‌عنوان یکی از سیگنال‌های تجربه‌ی صفحه استفاده می‌کنه، نه از نمره‌ی آزمایشگاهی. و این سیگنال در برابر کیفیت و ارتباط محتوا وزن کمی داره. سرعت «تساوی‌شکن»ـه، نه جادو. 🪄

❌ «یه افزونه نصب کنم، همه چیز درست می‌شه»

افزونه‌ها کمک می‌کنن، ولی نمی‌تونن یه قالب سنگین، هاست کند یا ۱۵ اسکریپت تبلیغاتی رو جبران کنن. گاهی هم با ترفندهای نمایشی فقط نمره‌ی آزمایشگاهی رو بالا می‌برن و کاربر واقعی هیچ فرقی حس نمی‌کنه.

❌ «نمره‌م دیروز ۹۲ بود، امروز ۸۴؛ سایتم خراب شد!»

نوسان چند نمره‌ای کاملاً طبیعیه. شبکه، بار سرور و اسکریپت‌های بیرونی هر لحظه فرق می‌کنن. چند بار تست بگیر و روند رو ببین، نه یه عدد تکی رو.

❌ «دسکتاپم ۹۸ـه، پس مشکلی ندارم»

تست موبایل با گوشی ضعیف‌تر و اینترنت کندتر شبیه‌سازی می‌شه و بیشتر کاربرهات هم با موبایل میان. ملاک اصلی، موبایله. 📱
